# Agentic SDLC Governance

How large engineering orgs run many coding agents at once, and how vendors are productising the governance layer underneath that.

## Where this stands

The category went from "a pattern three companies published about" to "a named control plane with an analyst Wave behind it" in two weeks. The consistent finding across every source is that the hard problems are specification and plumbing, not model capability. Forrester's breakdown of negative-ROI agent deployments at 12 months puts **41 percent on unclear success criteria, 33 percent on insufficient tool or data access, and 26 percent on evaluation-coverage drift.** None of those three is a model problem.

The term "governance layer" hides four separable problems, and vendors rarely say which one they solve: **what can this agent reach** (access and permissions), **what did it actually do** (audit and system of record), **what is it allowed to do without asking** (policy and approval gates), and **what did it cost and was it worth it** (attribution and ROI). Most products do one or two well.

Two independent results now say the same thing about verification: put the control outside the model, and vary the **evidence source** rather than the model doing the checking. A cross-model vote over shared evidence approves 62.9 percent of unsafe agent proposals; the same vote over an independent source approves 22.9 percent.

The throughput story is real and decays at every gate: agent-driven activity is up **180 percent at the commit level, 50 percent at the project level, and 30 percent at actual releases.**

## Open questions

- Does the control plane consolidate into tools teams already run (Atlassian, GitHub) or into a new procurement category? Forrester's Q4 Wave will push the second answer regardless of which is true.
- Nobody has published a credible cost model for the Verification Tax. Every vendor quotes throughput gains and none quotes the gate cost.
- The gates that exist all target correctness. ImpactGate is the first to target structural decay, and there is no equivalent for fabricated fixtures, silently narrowed scope, or tests written to the implementation.
- Does telling an agent the gate threshold in advance change its planning? Untested, and cheap to test.
- Gartner's position that applying *uniform* governance across all agents leads to failure is the counterweight to centralising everything, and nobody has published a tiering scheme that operationalises it.

## 2026-09-16

**ImpactGate scores the structural decay a change adds and gates the merge on it.** Apache-2.0, Python, and it publishes its formula rather than hiding a score: `impact = files_changed * Σ max(WMC_other, 1) * CC * Δlines` summed over changed functions, where `WMC_other` is the weighted method count already present in the container being edited, measured on the **pre-change** state. Read the terms and the incentive structure falls out. `Δlines` and cyclomatic complexity charge you for the size and branchiness of what you wrote, `files_changed` charges you for spreading a change across the codebase, and `WMC_other` charges you for **where you put it**: the same twenty-line method costs far more added to a class that already has forty methods than to one with three. It is not measuring whether your code is complex, it is measuring whether you made an already-bad structure worse, which is exactly what code review catches when a human has time and misses when they do not.

Thresholds live in `.impact-gate.yml` with `warn_at`, `block_at`, and an `enforcement` mode of off, warn, or block, all overridable by CLI flag, plus a tolerance multiplier adjustable per CI run. Defaults are warn at 50,000 and block at 200,000 impact units, and those absolutes are meaningless out of context, which the tool knows: the more interesting mode is **percentile grading**, blending a seed corpus distribution from 20 open-source repos with your project's own accumulating baseline, weighted `w = n/(n+K)` with `K` defaulting to 200 commits. A fresh repo is graded mostly against the open-source prior; after a few hundred commits it is graded mostly against itself. Files over 200,000 lines are skipped as presumed generated. Integration covers a GitHub Actions composite action, a GitLab CI template, a Jenkins snippet, a git pre-commit hook, and `ghcr.io/officefloor/impact-gate`. The research basis is the author's own "Measuring the Blast Radius of Change" writeup, a single-author blog post rather than peer-reviewed work.

Why it matters here specifically: every existing gate answers "is this change correct?" An agent is quite good at producing changes that are correct and locally sensible while being structurally the worst available option, because it optimises for the diff in front of it and has no stake in the shape of the file in six months. `WMC_other` is a cheap deterministic proxy for that stake. The interesting second-order move is that it is a measure an agent can be told about in advance: publish the threshold in the repo's agent instructions and "refactor the container first, then add to it" becomes the cheaper path rather than a thing a reviewer has to ask for. The obvious objection is Goodhart, since a measure charging for `Δlines` and `WMC_other` can be satisfied by scattering a change across many new small files, and only the `files_changed` multiplier counterweights that. ([GitHub](https://github.com/officefloor/ImpactGate), [HN](https://news.ycombinator.com/item?id=49726329))

**Datamimic gives coding agents deterministic test data instead of letting them invent a test world, and determinism is the actual product.** It is contractually specified: same engine version plus same model plus same seed yields **byte-identical output** across machines and runs, verified per service on every CI run by architecture gates, with a `determinism_proof.content_hash` per output for audit re-execution, UUIDv5 entity identifiers stable across runs, and a single wall-clock source of truth with raw `datetime.now()` forbidden in production code. That last detail is what makes the determinism claim credible rather than aspirational: they had to ban clock reads to get it.

Community Edition is **MIT-licensed**, with the Python execution engine, multiprocessing with optional Ray, domain services, schema validators, deterministic ISO 8601 time-series, and referential integrity across parent-child relationships, targeting PostgreSQL, Oracle, MongoDB, MySQL, SQLite, and CSV/JSON/XML/XLSX. The commercial Enterprise Platform adds a Rust fastpath, ML and auto-regressive generation, keyset and manifest building from live schemas, distributed billion-record execution, a probability-scored PII scanner, coordinated multi-system execution across Oracle/MongoDB/Kafka with referential integrity preserved, RBAC, audit logs, approval flows, a scheduler, and EDIFACT, SWIFT MT, and HL7 v2.x/FHIR message templates. It is already deployed in regulated EU banking environments and supports air-gapped installation.

The MCP adapter is optional and deliberately thin, exposing **four** operations (`reference`, `scaffold`, `check`, `dry-run`) and explicitly keeping domain generation inside Python and the CLI rather than duplicating logic across the MCP path. The agent scaffolds a descriptor, checks it, dry-runs it, and the deterministic engine does the actual work through the normal code path, so the output an agent produces equals the output CI produces. The differentiator against Faker and Mimesis is domain coherence, and their own example is the sharp one: Faker will happily generate a 25-year-old with Alzheimer's because it fills fields independently. Limitations they state themselves: CE's PII field identification is **manual**, with no automated scanner, and the pseudonymisation disclaimer is appropriately careful, since GDPR anonymisation status depends on complete field coverage and a re-identification risk assessment across the whole dataset.

The connection to the verification-gate result: independent evidence only works when it comes from somewhere other than the thing being verified. A fixture an agent invented for itself is not independent evidence. A provenance-hashed fixture generated from a committed seeded descriptor is. ([GitHub](https://github.com/rapiddweller/datamimic), [HN](https://news.ycombinator.com/item?id=49722276))

## 2026-09-15

**A September arXiv paper on verification gates produced the most directly actionable finding of the window: evidence source diversity beats model diversity by a wide margin.** VP-CONTROL benchmarks verification for agents taking state-changing actions across 48 task templates and 2,880 scenarios in six fault regimes. A cross-model vote over **shared** evidence approves **62.9 percent** of unsafe proposals. The same vote over an **independent** source approves **22.9 percent**. The source effect is **40.9 percentage points**; model diversity contributes **11.3**. Their portfolio controller reaches 1.9 percent unsafe execution with 38.2 percent automated safe coverage on a locked test, and generalises badly, at 16 to 26 percent risk on unseen fault families. The design rule falls straight out: asking three models to check the same artifact is close to theatre, and a transactional partial guard only covers the failures it was written for, while a full atomic guard recorded no unsafe effects across 216 episodes. ([arXiv 2609.10969](https://arxiv.org/abs/2609.10969))

**The companion synthesis paper names the control plane properly.** It compiles peer-reviewed SE research and production reports through September 2026 into four concepts: the **Agentic SDLC Throughput Paradox**, **Production-Qualified Change**, the **Verification Tax**, and an **Agentic SDLC Control Plane** that allocates autonomy against cost, reliability, and human-attention budgets. Its headline number is the one to carry into any agent-ROI conversation: a study of more than 100,000 GitHub developers found agent-driven coding activity up **180 percent at the commit level, 50 percent at the project level, and 30 percent at actual releases**. The throughput gain is real and it decays at every gate. ([arXiv 2609.04681](https://arxiv.org/abs/2609.04681))

**Forrester launched an Agentic Development Platforms vendor landscape, with a Wave planned for Q4.** Its framing matches what this thread has tracked since 09-03: vendors now compete on orchestration, enterprise context, governance, model agility, and cost transparency rather than on code generation. The analyst-firm category existing at all is the signal, because it means procurement will start asking for a control plane by name. ([Forrester](https://www.forrester.com/blogs/launching-the-agentic-development-platforms-vendor-landscape-q3-2026/))

## 2026-09-14

**The governance layer is consolidating into agent registries, and the failure-mode data is now specific enough to design against.** Credo AI's Agent Registry (public preview) catalogues internal and third-party agents with risk assessments and named human-oversight intervention points; Kore.ai's Agent Management Platform sells a vendor-agnostic control plane spanning LangGraph, CrewAI, AutoGen and others. The useful number is Forrester's breakdown of agent deployments showing **negative ROI at 12 months**: **41 percent unclear success criteria, 33 percent insufficient tool or data access, 26 percent drift in evaluation coverage.** Not one of those three is a model problem. All three are specification and plumbing problems.

**The commonly-missing controls are equally mundane:** SSO unconfigured, audit logs not wired to SIEM, PR gates unenforced, no sandbox isolation for agent execution. Read that list against MCP's agent-identity roadmap: the standard is arriving at roughly the moment orgs discover they need it. Separately, GitHub Copilot Workspace now supports multiple specialised agents working simultaneously on different parts of a codebase, which is the same many-agents-at-once problem showing up inside the IDE. ([Kosmoy comparison](https://www.kosmoy.com/resources/blog/best-ai-agent-governance-platforms-2026/), [Northflank](https://northflank.com/blog/enterprise-ai-coding-agent-deployment))

## 2026-09-11

**Atlassian shipped a governance layer for agentic engineering across Jira and DX, and it was the category's most directly usable release so far.** The capabilities split cleanly into three groups. *Grounding*: **Code Context** provides secure intelligence across multi-repository codebases via the Teamwork Graph (open beta, rolling out to paid customers), and **Agent Context Controls** let platform teams govern which Jira and Confluence spaces agents may access (GA in coming months). *Autonomy*: agent loops in Jira automate backlog-to-pull-request, **Standards** lets an org define coding standards once and map them across repositories, and AI review puts a dedicated agent on pull requests checking against those standards, all three in private early access. *Measurement*: **DX for Agentic Development** measures AI impact across throughput, quality, adoption, and cost (GA this quarter), and a Jira Agent Usage Dashboard correlates agent sessions to work items (GA in coming months).

**Agent Context Controls is the reach-and-access half, and the detail is the whole point.** The permission boundary is set centrally by the people who own the tooling, rather than inherited from whichever user happened to authorise the agent. That is precisely the failure Cymphony documented: an external collaborator stood up an unsanctioned Claude instance that used the collaborator's own access to scan thousands of sensitive files. If an agent's reach is a property of the platform rather than a side effect of a user's credentials, that class of incident becomes structurally harder.

**DX for Agentic Development is the attribution half**, and GA this quarter makes it the nearest-term piece. The Jira Agent Usage Dashboard turns "we run a lot of agents" into "this epic consumed this much agent work and shipped," which is the same conceptual move as Ramp Labs' purpose, outcome, and cost records, arriving pre-built inside the issue tracker rather than as something to construct.

**The framing statistic is the useful one:** Atlassian's 2026 AI SDLC study found **94 percent of engineering leaders report using AI while only 6 percent have systems to scale it across the full SDLC.** Their own claim that teams using more Atlassian context "shipped roughly 64 percent more per developer" is vendor-sourced and should be treated as marketing. What matters is the adoption cost: the Uber and Port versions of this pattern require adopting a platform, while this arrives in a tool that is already running. ([announcement](https://www.stocktitan.net/news/TEAM/atlassian-launches-system-to-coordinate-and-accelerate-agentic-2lmhp7bq3wls.html))

**What a "governance layer" actually means.** Four distinct problems hide inside the term: **reach** (access and permissions), **audit** (what it actually did), **policy** (what it may do without asking), and **attribution** (what it cost and whether it was worth it). Mapped onto what has come up here: Uber's Context Graph and Port's Context Lake are *reach* solutions, making organisational facts available to agents in a structured way. Cymphony is *reach* plus *audit*, as an identity graph spanning humans and agents. Meta's Muse Sentinel is pure *policy*, a separate permitting agent that must approve every connector action and network request at L4 and L7. Ramp Labs' semantic layer is *attribution*. The MCP Enterprise-Managed Authorization extension is *access* standardisation. MCP registries and skills catalogs are discovery with access enforcement attached. Two structural points matter for anyone picking. **Gartner's position, that applying uniform governance across all agents leads to failure, is the important counterweight to centralising everything:** a read-only reporting agent and an agent with write access to production do not warrant the same gate, and treating them identically produces either paralysis or theatre. And the honest constraint is that the vendor-cited figure of **88 percent of agent pilots never reaching production** names deployment infrastructure, isolation, governance, compliance, and data residency, as the blocker rather than model capability, which is self-serving coming from governance vendors but consistent across independent sources. ([Gartner](https://www.gartner.com/en/newsroom/press-releases/2026-05-26-gartner-says-applying-uniform-governance-across-ai-agents-will-lead-to-enterprise-ai-agent-failure))

**Helix, Shopify's checkpoint system, is the most transferable artifact in this whole topic.** The mechanism is a refusal to accept one-shot generation. A developer points Helix at a specific screen in the React Native codebase; Helix reads the existing implementation and then **proposes a sequence of checkpoints**, small ordered slices each sized to be reviewable in minutes, and implements them one at a time in Swift or Kotlin, each building on the last. The discipline is in the gates: every checkpoint must clear four before the next starts. It proves its behaviour with tests, it matches the running app under visual review, it survives **two adversarial code reviewers**, and it gets a human's explicit approval before commit. Nothing advances on a partial pass. **The design insight worth stealing is that the unit of review is chosen by the system rather than by the agent's natural output size**, which is precisely the lever that prevents a 35-hour runaway of the kind Ronacher describes. The second-order piece is a feedback loop: Helix retains the feedback from each review cycle, so the agent earns more autonomy as the migration progresses without the oversight gates being removed. Autonomy grows from accumulated review signal on this specific codebase, not from a configuration flag. Shopify credits this for rebuilding the Shop app natively in 12 weeks. ([Shopify Engineering](https://shopify.engineering/back-to-native))

## 2026-09-10

**Shopify is migrating back to native Swift and Kotlin from React Native, and the stated reason is coding agents.** This moved the category somewhere new. Shopify went React Native in 2020, finished migrating its largest app in November 2024, and reported 86 percent code unification and 1.8M redundant lines eliminated. Their post says plainly that "LLMs changed one of the core assumptions behind our 2020 decision": agents can now implement a feature on one platform using the other as reference, ramp developers outside their primary stack, and handle translation, testing, and review. So the *benefit* of sharing one implementation shrank while the benefits of building natively, closer to platform capabilities and first-party tooling with fewer framework layers, stayed put. They are doing greenfield rebuilds rather than gradual brownfield migration, on the theory that agents make reconstruction faster than incremental porting.

**Why this is different from the rest of the category:** the Uber, Port, and Ramp cluster was about *operating* many agents through context graphs, ROI attribution, and governance. Shopify is the first case of agent capability changing an architectural decision that had nothing to do with AI. The cost of maintaining two codebases fell because agents can port and verify between them, so a cross-platform framework adopted to avoid that cost stopped paying for itself. Expect more of this shape, where the second-order effect on technology selection matters more than the direct productivity claim. 254 points on Hacker News. ([Shopify Engineering](https://shopify.engineering/back-to-native))

**Agent skills catalogs became a first-class artifact type**, with OpenAI publishing an official skills catalog and Vercel Labs shipping an open agent-skills tool, the practitioner-layer counterpart to the Portkey and MCP-registry consolidation.

## 2026-09-09

**Cymphony exited stealth and reframed the problem from context to identity.** \$30M total, including a \$25M Series A co-led by Sequoia and SMBC's Fin Atlas Beyond Fund at a \$100M-plus valuation. It sells a **"workforce graph"** that maps employees and AI agents in one identity graph: what each can access, what sensitive data it touches, and what risk that creates. The Uber, Port, and Ramp cluster treated many-agents-at-once as a context and ROI-attribution problem; Cymphony treats it as an identity and access problem, and its selling evidence is **discovered exposure**. At one US public company it found about **85,000 files** that had quietly become reachable by AI tools. At another, an external collaborator had stood up an unsanctioned Claude instance that used the collaborator's existing access to scan thousands of sensitive files. **Both of those are failure modes of a *successful* agent rollout, not a failed one.** ([TechCrunch](https://techcrunch.com/2026/09/09/sequoia-doubles-down-on-cymphony-as-ai-agents-create-new-enterprise-security-risks/))

**Meta's Muse Sentinel is the cleanest published statement of the agent-sandboxing pattern.** Muse runs in a dedicated per-user VM in Meta's cloud that hosts both the agent and the user's personal data, with its own browser, and Meta says the agent has no visibility into passwords or payment methods. A separate **Sentinel** agent approves every connector action and every network request, **at both layer 4 and layer 7**. Muse proposes; only Sentinel permits. That two-agent proposer-permitter split is implementable without Meta's stack, which is why it went on the radar. ([SiliconANGLE](https://siliconangle.com/2026/09/08/meta-debuts-its-secure-by-design-personal-ai-agent-muse/))

**The AI-asset-registry layer is consolidating.** The open-source MCP Gateway & Registry has outgrown MCP and now registers agents, skills, and custom entities behind one authenticated gateway that enforces access and logs every call, and Portkey shipped a Skills Registry pitched explicitly at platform teams owning Claude Code, Cursor, and Codex across an org. The converging pattern: **register once, discover by natural-language search, reach through a single gate that records everything.** Same shape as a service catalog, one abstraction level up.

## 2026-09-04

**No new items, and the honest note was that the load-bearing assumption is unproven.** The Ask HN "who is using MCP in production" thread was the closest adjacent signal, and production MCP adoption is the load-bearing assumption under most of the governance-layer thesis. That thread suggested it was still an open question in practice.

**Uber's Context Graph, architecture and build.** Two Uber sources describe two different scales for the same underlying idea, and it is worth being precise rather than treating them as one number. Uber's own blog and the Port newsletter describe a unified AI Context Graph of **40 million entries across 150 node and edge types**, aggregating mobile app structure, backend services, the data lake, design docs, Jira tickets, incidents, and bugs, replacing the 20 to 30 separate systems agents previously had to query one at a time. A separate writeup drawing on a Neo4j customer story cites **24 million nodes and 80 million edges across 86 node types and 117 edge types** for what Neo4j calls Uber's "Config Knowledge Graph," a narrower graph purpose-built for configuration validation. Neither source states whether these are the same graph at different points in time or two related efforts. Treat them as separate data points.

**The Neo4j case study is the one with real build detail.** The concrete problem: with 3,000-plus microservices, 3,500-plus feature-flag namespaces, and operations in 15,000-plus cities, configuration lived in silos, so a driver could pass onboarding in one system but fail dispatch eligibility for a premium product in another, a mismatch that multiplied across 8 million-plus earners cost real revenue. Uber tried SQL first, where recursive CTEs and self-joins became unmanageable, then key-value stores, too many network round trips per relationship traversal, then document-based RAG, which could not traverse entity relationships at all, before landing on a graph. The schema models the business domain directly as nodes and typed relationships, so a question like "what documents does a Boston driver need for Uber Comfort" becomes a graph traversal instead of a query across multiple owning systems. It runs on Neo4j AuraDB on GCP, uses ACID-compliant transactions so a bad config change rolls back entirely rather than partially landing, and is exposed to both humans and LLMs via MCP. **The detail worth sitting with: two engineers built this to production in under twelve weeks.** That is a small scoped team building a narrow well-defined graph, a meaningfully more achievable starting point than "build Uber's Context Graph." ([Neo4j customer story](https://neo4j.com/customer-stories/uber/))

**Three different shapes for a central knowledge base.** Uber's Context Graph, Port's Context Lake, and Chopin's decision layer are three genuinely different architectural answers to how agents get grounded organisation-specific context. **Uber's pattern is a property graph of facts**: typed nodes and typed edges representing what exists and how it relates, queried by traversal, strongest when the domain really is relational and the relationships are the valuable part, and expensive to build well because someone must design the schema before any data loads. **Port's Context Lake is a catalog with a semantic layer bolted on**, not a graph agents traverse freely: you define blueprints (service, environment, team, deployment, incident) as the entity model, then 100-plus integrations continuously populate real entities against those blueprints, so freshness comes from live sync rather than batch ETL. The four kinds of context Port's docs name, **domain knowledge, operational state, the human layer of ownership and policy, and the actions an agent is allowed to take**, are a useful checklist for scoping any KB project independent of the tool, because most first attempts capture only the first and miss the other three. **Chopin is neither a graph nor a catalog**: a document with a durable decision ledger next to the prose, so a later rewrite cannot silently change what was decided. Lightest weight, no upfront schema, and nothing to traverse structurally. The practical read: do not start by picking a technology. Start by asking which of three problems you are solving, "what exists and how does it relate" (graph), "what is the live state and who owns it" (catalog plus semantic layer), or "what did we decide and why, in a form that survives edits" (decision ledger).

## 2026-09-03

**The category's founding items, all forwarded directly rather than found via search.**

**Uber published its "AI Software Factory" operating model:** over **70 percent of PRs now originate from agents**, code productivity roughly doubled year over year, resting on six platform pieces (a 40M-entry Context Graph, a 2,500-plus item Skills Registry, an MCP Gateway serving 1,000-plus tools, an LLM Gateway handling 100M-plus daily requests, pre-warmed Kubernetes environments, and a unified assistant interface). The stated argument: **the platform has to exist before any agent workflow does, or agents become "scripts that break the first time a repo moves."** ([Port newsletter](https://newsletter.port.io/p/how-uber-built-a-software-factory))

**The six pieces support four concrete workflows.** *Spec-to-prototype*: an engineer tags Uber's assistant in Slack, it queries the Context Graph to size the opportunity, generates two A/B mockup variants, and reasons about which existing screens and services can be reused, compressing weeks of alignment into one session. *Code generation with validation*: Minion, Uber's coding agent, writes frontend and backend code in warm Kubernetes environments but **stops at a draft PR rather than pushing to shared CI**, running three inner-loop checks first: static analysis, visual validation that boots a simulator and diffs screenshots against the design spec, and integration checks against a staging backend. *Self-healing CI and review*: routine CI failures get repaired automatically rather than bouncing to a human, and review runs in two tiers, a fast model on the agent's own machine and a deeper model in CI, with **every PR carrying a verification table of passed checks and screenshots so a reviewer judges feature merit rather than re-checking basics.** *Managed maintenance automation*: services opt into scheduled maintenance skills (feature flag cleanup, stale A/B variant removal) on a fixed cadence, most often Sundays, capping how many diffs land on engineers at once, and the loop self-improves as PR outcomes become training data for the next skill revision. Scale numbers: **20,000-plus skill runs daily, 300 team-specific assistant versions built within a single month, 20,000-plus assistant sessions daily.** The framing worth keeping: Uber's stated constraint shifted from "can we build it" to "should we build it."

**Port.io is the productised version of the same governance layer:** a Context Lake, agent, MCP, and skills registry with governance, human-in-the-loop workflow orchestration, and ROI tracking, aimed at what they call "agentic chaos," meaning uncontrolled agent proliferation once every team has its own tools with no central visibility. Port raised a \$100M Series C in December 2025 led by General Atlantic at an \$800M valuation, \$158M raised to date, and reports 300 percent revenue growth across roughly 200 employees. Customers include GitHub itself, British Telecom, Visa, Sonar, StubHub, Serko, and Nando's. **The fact that GitHub is a paying Port customer while simultaneously running its own from-scratch research prototype in this space (Chopin) is a real signal that even a company with GitHub's resources does not consider agent-planning tooling and agent-governance tooling the same problem.**

**Ramp Labs built a semantic layer turning raw agent traces into purpose, outcome, and cost records**, so agent work can be measured against product and business metrics the same way any other spend is. Over three weeks it processed about **200,000 agent runs into about 250,000 discrete work items**. The mechanical pipeline: raw traces get combined into complete agent runs by stitching related sessions together, then each run is split into work items, a work item being one distinct objective the agent pursued within that run. Each work item records its goal and outcome, gets labeled by kind of work, product or platform domain, and technical surface touched, then gets linked back to the run's model spend, owner, team, and repository. The stated thesis, worth quoting directly: **"Measuring AI ROI cannot start with tokens or model calls. It has to start with the objective an agent was asked to pursue and the outcome it helped produce."** That names the actual missing join key, objective and outcome, rather than just asserting spend should be judged on value. ([Ramp Labs](https://x.com/RampLabs/status/2094871453879402747))
