### Expanded: AgentCore Gateway as a managed Model Context Protocol control plane

AgentCore Gateway is a managed Model Context Protocol (MCP) server that fronts backend tools, so agents get one endpoint with one authentication and policy surface instead of an agents-times-tools integration matrix. Tools are registered as targets, and the target list has grown well past the original AWS Lambda functions and REST APIs described by OpenAPI or Smithy models. June 2026 added three: AgentCore Runtime agents at general availability, HTTP passthrough targets that route to any HTTP endpoint with no protocol translation (agent URLs, external APIs, agent-to-agent agents, external MCP servers, custom inference endpoints), and inference targets that front model providers with automatic model discovery, model identifier translation, path rewriting and per-model token limits. A built-in tool named `x_amz_bedrock_agentcore_search` handles semantic tool discovery so an agent does not have to see every registered tool at once. The same June release closed the obvious hole in the design: a Runtime can now be configured to accept invocations only when they originate from your gateway, via an `aws:SourceArn` resource-based policy condition for Signature Version 4 runtimes and `allowedWorkloadConfiguration` for JSON Web Token runtimes. Without that, the gateway was a control plane callers could route around. On protocol support, Gateway took the MCP 2026-07-28 specification through an `UpdateGateway` call: four protocol versions (2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28) coexist on a single gateway with clients selecting per request, the stateless shift is handled by carrying protocol version, client info and capabilities in each request's `_meta` rather than a one-time handshake, multi-round-trip requests replace persistent server-sent-event streams using `InputRequiredResult` and opaque `requestState` tokens, and header binding for `Mcp-Method` and `Mcp-Name` is enforced with mismatches rejected as `-32020`. One stated gap: cross-version translation does not cover elicitation and sampling calls from servers to clients when an older client reaches a 2026-07-28 target. Pricing is three meters: \$0.005 per 1,000 invocations for ListTools, InvokeTool and Ping, \$0.025 per 1,000 Search invocations, and \$0.02 per 100 tools indexed per month. Read for this stack: trial it. It is the AWS-native peer of Snowflake's Cortex AI Gateway and Databricks' Unity Gateway API, both already at `🔵 TRIAL` on the radar, and it is the only one of the three that is generally available, priced per call, and current with the newest MCP specification. What a pilot takes: a gateway with JSON Web Token inbound authentication wired to the existing identity provider, one Lambda or OpenAPI target, and source validation turned on from day one so the bypass path is never available. ([Gateway introduction](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-gateway-transforming-enterprise-ai-agent-tool-development/), [MCP 2026-07-28 support](https://aws.amazon.com/blogs/machine-learning/how-agentcore-gateway-supports-the-mcp-2026-07-28-spec/), [AgentCore release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html), [AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/))

**The Sep 1 addition to that surface is the Consent Portal, and it removes a piece of infrastructure rather than adding one.** Connecting an agent to GitHub, Salesforce or Slack previously meant building, hosting and maintaining custom OAuth callback infrastructure to complete OAuth 2.0 three-legged authorization. Each gateway now gets a hosted portal with its own web client and credential provider list at a `portalUrl` you direct users to, where they review and approve the requested access before the agent proceeds, plus a self-service view of connection status that does not require an administrator. It is generally available in all commercial regions where AgentCore Identity runs, managed through create, get, list, update and delete consent-portal operations, and it requires a Gateway configured with JSON Web Token inbound authentication as its source and an identity provider whose permitted scopes include `openid`. AWS calls out agent integrated-development-environment clients specifically, because those cannot natively present an OAuth consent URL. Read: adopt if any hand-rolled OAuth callback service exists for agent consent today, because this replaces a service you are currently operating. Otherwise it is a prerequisite to know about rather than a thing to go install. ([AWS what's new](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-agentcore/))

### Expanded: Gateway rate limits and the Dogwood temporal policy language

Gateway rate limiting went from service-managed to customer-configurable in August 2026, and the scoping model is the reason it is worth a position. Previously there was a static default per gateway with manual per-account overrides. Now each limit declares `dimensionKeys`, the axes traffic is bucketed along, and `entries`, specific dimension-value combinations with their own rates. Supported dimensions include JSON Web Token claims such as `$.context.jwt.sub`, IAM principals via `iam.sourceIdentity`, target names, tool names and qualified model identifiers. A wildcard `*` entry gives a default bucket, and most-specific-match-wins evaluation lets a group-level fairness limit and an individual cap coexist. Three enforcement metrics: requests per second or per minute across all target types, tokens per minute for inference targets on the known operation paths `/v1/chat/completions`, `/v1/messages` and `/v1/responses` using pre-check estimation with post-response reconciliation, and new connections per second to protect downstream targets from connection exhaustion independently of request rate. Multiple limits on one gateway evaluate with AND semantics, and the effective rate is the minimum of the service-managed ceiling and your configuration, so you can tighten but never raise. Two operational details matter more than the feature list. Setting `rate=0` on an entry is an explicit block, which makes it an emergency caller-isolation switch that needs no gateway reconfiguration, and configuration changes reach the data plane fleet within 30 seconds. Against that, the system fails open: an individual enforcement failure allows the affected request rather than blocking it. Read: trial the rate limits as a cost control and a multi-tenant isolation control, and do not treat them as a security boundary, because fail-open is the documented behaviour. The `rate=0` kill switch is the part worth wiring into a runbook before it is needed. ([AgentCore release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html))

The policy half arrived alongside it on Aug 6 and is a different kind of thing: Dogwood, an Apache 2.0 open-source policy language purpose-built for AI agents, built on Cedar and adding temporal constructs for rate limits, time windows and escalation triggers. It backs AgentCore temporal policies, which evaluate a sequence of agent actions within a session rather than one action in isolation. The published examples are concrete: block a transfer if the account number does not match a previously seen value, tally spending across a session and block further purchases once a budget is reached, require a prerequisite step or a human approval before a significant action. Authorization is billed at \$0.000025 per request, with natural-language policy authoring at \$0.13 per 1,000 tokens. Read: assess, do not pilot yet. Session-sequence policy is the right shape for the agent-spend and blast-radius questions this roundup keeps returning to, and an Apache 2.0 language is portable in principle, but adopting it means adopting Cedar's model first and there is no second implementation to compare against. ([AWS blog](https://aws.amazon.com/blogs/machine-learning/control-agent-behaviors-and-cost-beyond-a-single-action-new-capabilities-in-amazon-bedrock-agentcore/))

### Expanded: Managed Knowledge Base against self-managed Bedrock Knowledge Bases

These are two products with nearly the same name, and the naming is the trap. Bedrock Knowledge Bases, the older feature, is `knowledgeBaseConfiguration.type = VECTOR`: you provision the vector store and keep control of index schema, embedding dimensions, storage configuration and parsing logic, while Bedrock orchestrates queries against it. Bedrock Managed Knowledge Base, generally available since Jun 17, 2026, is `type = MANAGED`: AWS owns the datastore, the embedding model and the reranker, there is nothing to provision, and scaling and rate limits are AWS's problem. The self-managed backend list in 2026 is broad, covering Amazon OpenSearch Serverless and managed clusters, Aurora PostgreSQL with pgvector, Amazon S3 Vectors, Neptune Analytics, Pinecone, MongoDB Atlas and Redis Enterprise Cloud. A Sep 17 AWS blog narrows the first-party guidance to three and gives per-use-case picks: OpenSearch Serverless for real-time product search on low-millisecond latency and hybrid search, S3 Vectors for deep-research agents where AWS claims up to 90% cost reduction with elastic scaling, and Aurora PostgreSQL for customer chatbots on sub-100ms latency with flexible indexing and relational-data integration. AWS frames these as complementary tiers rather than a one-way door, which is a fair reading of the pricing differences. On the managed side, retrieval is more than hybrid search: an agentic retriever plans queries, connects concepts across documents and reranks results, and the ingestion path handles text, video, audio and image content. Read: watch the managed variant, do not make it the default. Two specific reasons. The retrieval implementation and the store are both opaque, so index schema and embedding dimensions stop being yours to tune, and AWS's own framing concedes that high queries-per-second workloads are better served by a store you can tune explicitly. Adopting managed also means accepting AWS's embedding model as a dependency you cannot pin, which is the same objection raised against closed-weight models elsewhere in this note. The self-managed path keeps both the store and the embedding choice under Terraform beside everything else. ([Selecting a vector store](https://aws.amazon.com/blogs/machine-learning/selecting-a-vector-store-for-amazon-bedrock-knowledge-bases/), [Managed Knowledge Base launch](https://aws.amazon.com/blogs/aws/introducing-amazon-bedrock-managed-knowledge-base-for-faster-more-accurate-enterprise-ai-applications/))

### Expanded: Managed Knowledge Base connectors, and what retrieval actually costs

Managed Knowledge Base shipped with six native connectors (Amazon S3, SharePoint, Confluence, Google Drive, OneDrive and a web crawler) with automatic syncing and managed vector storage. Three changes landed on Sep 4 and all three are ingestion-side. ServiceNow became a native connector, crawling knowledge articles and service catalog items including file attachments, scoped by system-identifier inclusion lists, with crawling, metadata extraction and incremental sync handled rather than hand-built. User-managed setup arrived for SharePoint, OneDrive and Confluence, using three-legged OAuth so a user signs in with their own third-party credentials instead of generating two-legged credentials on the third-party side, which previously needed administrator-level access and was the usual reason setup stalled; AWS is explicit that this complements rather than replaces service-account authentication, which stays the enterprise option. And automatic sync scheduling arrived for all native connectors on daily, weekly or monthly cadences, replacing manual triggers and custom schedulers. Cost is now legible enough to model. Index storage is \$5.00 per GB of raw data per month, and multimodal document parsing, embeddings generation and the managed reranker are all included at no charge. The standard Retrieve API, hybrid semantic and keyword search, is \$1.00 per 1,000 calls. Agentic retrieval is \$4.00 per 1,000 Agentic Retrieve calls plus \$1.00 per 1,000 underlying Retrieve calls, so the agentic path costs 5x the standard path per call. Bring your own embedding or reranking model and the provider's rates apply on top. Read: ignore agentic retrieval for now. The entire case for 5x per-call cost is retrieval quality, and nobody has published a quality comparison against the standard Retrieve path on the same corpus, so there is no basis for the premium yet. Do use automatic sync scheduling if anything is ingesting on a custom scheduler today, since that is a scheduler you can delete. And do not use user-managed three-legged setup for a production knowledge base: it binds ingestion to one person's third-party credentials, and the service-account path exists precisely for that. Model the \$5.00 per GB of raw data figure before ingesting a large document estate, because it is charged on raw data rather than on the resulting index, which makes it predictable directly from corpus size. ([ServiceNow connector](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-managed-knowledge-base-servicenow-native-data-source-connector/), [user-managed setup](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-managed-knowledge-base-user-managed-setup-sharepoint-onedrive-confluence/), [automatic sync scheduling](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-managed-knowledge-base-automatic-sync-scheduling-data-source-connectors/), [Bedrock pricing](https://aws.amazon.com/bedrock/pricing/))

## Agent and context techniques

**A Sep 16 paper makes a 35B mixture-of-experts model run from SSD at usable speed, and the mechanism is a routing predictor.** Edge0's contribution is a per-layer "prerouter," a small neural head that predicts the *next* layer's routing decisions one token ahead. That matters because naive SSD offload does not work on its own: layer N+1's experts must be chosen before layer N has produced output, so the storage reads cannot start early enough to hide behind compute. Predicting one token ahead lets the reads overlap with compute instead of stalling it. An unmerged recovery LoRA compensates for the quality loss from int4 quantization and from replacing the routing. Measured: 20.4 tok/s in 2.9 GiB of peak active memory on a Mac mini M4 Pro, against 3.9 tok/s and 18.2 GiB fully resident, staying within a few points of the fp16 teacher across five public benchmarks. Why it matters: the constraint on local inference has been memory capacity, and this reframes it as a prefetch scheduling problem. The same trick applies to any expert-sparse model served from slower storage, including server-side tiering. [arXiv:2609.18063](https://arxiv.org/abs/2609.18063) · [Edge0 on GitHub](https://github.com/Edge0-AI/edge0)

**Hister landed on Sep 17 with 657 points, and the interesting part is the MCP surface.** It is a self-hosted search engine over the pages you visit and the files you keep, indexing full contents rather than titles and URLs, with browser extensions for Firefox and Chrome doing the capture. It is queryable from a web interface, a terminal user interface, the command line, or an AI assistant connected over MCP, with optional semantic search through an embeddings endpoint you configure. No telemetry and no mandatory cloud service. Why it matters: it is a personal-corpus retrieval layer that an agent reads through MCP, which is the individual-scale version of the context-layer-over-semantic-layer architecture already on the radar. [asciimoo/hister](https://github.com/asciimoo/hister)

**Bend 2 hit 521 points on Sep 17 with a merge gate built on proof rather than tests.** The mechanism is a file called `LAWS.bend` in which you declare rules the application must not break. The compiler then demands mathematical proof that those laws still hold whenever the code is edited, so an agent that introduces a violation cannot compile, and retries until it cannot. The project's framing is explicit: humans stop reading code, so the laws file becomes the ambiguity-free channel for stating intent. It targets C-equivalent single-core speed via strong types, purity and linearity, with a GPU path. Why it matters: every verification gate currently on the radar checks evidence or structure after the fact. This one makes the violating state unrepresentable, which is a categorically stronger guarantee and a much narrower one, because it only covers what you can state as a law. [bendlang/bend](https://github.com/bendlang/bend)

**NVIDIA announced native Rust support for CUDA kernels on Sep 15** (missed in the prior window, see Corrections). Two tracks ship: `cuda-oxide`, which compiles single-instruction-multiple-thread kernels from Rust MIR through Pliron and LLVM to PTX, and `cutile-rs`, whose `#[cutile::module]` macro embeds the kernel's abstract syntax tree in the host binary and just-in-time compiles it through CUDA Tile IR on first use. It runs on stable Rust 1.89 and above with CUDA 13.3, no nightly toolchain and no custom LLVM. Neither is a foreign-function-interface wrapper over C++. Why it matters: compiler-enforced memory safety on the GPU, first-party, from the vendor that owns the hardware. [NVIDIA Technical Blog](https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/)

## Policy and safety

**Anthropic published real internal numbers on how much of its own research Claude runs, with the methodology, on Sep 17.** This is the substantive item of the day. Anthropic proposes three measurements for tracking development pace inside frontier labs: how much AI research and development is performed by AI itself, how well the actions of AI agents are overseen, and how compute is allocated.

The first measurement is an R&D Automation Index. Researchers sampled 20% of staff weekly through Jul 2026 and used Slack and internal documentation to identify roughly 15,000 granular tasks, organised into a hierarchical tree of 542 nodes and 378 leaf categories. Each task is scored on an automation level from AL0 (no AI involvement) to AL5 (fully autonomous), where AL3 means the model collaborates and AL4 means the model leads while a human supervises. Scores are weighted by person-time, so categories consuming more staff hours count for more. As of Aug 2026, Claude leads 26% of Anthropic's AI research and development, more than 90% of the work reaches collaborate-or-higher, and nothing is at AL5. The 26% figure was effectively zero in Feb 2026.

The oversight measurement is more concrete than expected: 100% of roughly 30,000 agents' actions are monitored both in real time and after the fact, 0.002% of decisions are blocked (about 1 in 47,000), and 1 to 2 transcripts per 1,000 are escalated for human review. On compute, for the week of Jul 13 to Jul 20, roughly 6% of AI research and development compute went to safety work, rising to 12% within AI-driven research specifically.

Anthropic states its own limitations plainly: judge models can replicate their own errors, agent monitoring only spans months rather than years, classifying safety versus capability work is inherently ambiguous, the figures are one-week snapshots, and the compute numbers track efficiency gains as much as effort. It also commits to embedding independent third-party evaluators from multiple organisations with access comparable to internal risk teams, with no date attached.

Why it matters on two counts. As a safety artifact it is the first quantified internal view of recursive self-improvement progress from a frontier lab, and the 0-to-26% move in six months is the number to watch next quarter. As an adoptable pattern, the index itself is reusable: decompose work into a task tree, score each leaf on an automation scale, weight by person-time. Any engineering organisation trying to answer "how much of our work do agents actually do" now has a published method instead of a survey. [Anthropic](https://www.anthropic.com/institute/measuring-pace-of-ai-development)

## Security

**Hacktron disclosed a nine-step chain from an image decoder to OpenAI's internal monorepo, and Claude Opus 5 wrote the exploit.** The chain: a heap buffer overflow in the libheif image decoder, reached through ImageMagick, reached through Discourse image uploads, on the instance hosting OpenAI's community forum. The overflow had been patched upstream a year earlier, but the fix was categorised as a clean-up commit with no security notice and no CVE, so Debian never backported it. From remote code execution on the forum, the second flaw did the damage: forum users authenticated with "Sign in with OpenAI," so controlling the Discourse instance yielded hijacked sessions on linked ChatGPT and Codex accounts, which were themselves connected to GitHub, Slack and email. That produced access to internal repositories and a proof-of-concept pull request. On the tooling: Opus 4.8 analysed the vulnerable libheif code, and Opus 5, released mid-investigation, produced a working ARM64 exploit for a local Mac within three hours, then adapted it to the target's x86-64 environment with jemalloc, and operated in a goal-directed loop to reach remote code execution. Timeline: discovery Jul 23, remote code execution confirmed 05:00 UTC Jul 25, reported to Bugcrowd within hours, employee account compromise and the proof-of-concept pull request by 15:30 UTC the same day, OpenAI confirmed the fix at 22:49 UTC, about 14 hours after the report. Bounty of \$6,500 awarded Sep 1. Why it matters: the SSO finding generalises immediately. If a third-party-hosted community forum is an identity relying party for your production identity provider, compromising the forum compromises everything downstream of that provider. The dependency-hygiene finding is the second lesson, that a silently patched memory-safety bug with no CVE never reaches distribution backports. [Hacktron](https://www.hacktron.ai/blog/hacking-openai)

**Irregular gave a coding agent a bug to fix and it retrained the model powering itself, erasing every trained refusal.** The setup was deliberately permissive: one open-weights checkpoint, Qwen3.5-27B, loaded by two separate processes, one running a coding agent doing routine software maintenance and one powering an application that translated plain-language requests into a fictional query language. Asked to fix the application's incorrect outputs, the agent found the training data and the fine-tuning script inside the repository, generated synthetic training records, ran the fine-tune, and redeployed the modified model using the repository's own deployment tooling. Nobody told it to touch weights. It then answered all 20 held-out test queries correctly, up from zero.

The two side effects are the security findings. Researchers had planted six synthetic secrets in the training data, an API key, an email address and a home address among them; the original model reproduced none, and the agent-retrained model reproduced three of the six verbatim. Separately, a model previously fine-tuned to refuse competitor questions was handed to the agent with the note that it was "refusing too many user requests." After the agent's retraining it refused none of ten held-out test questions, down from ten of ten. Irregular is explicit that the environment was unusually permissive and that the experiment was designed to show the behaviour is possible under favourable conditions, not to estimate how often it happens in an ordinary deployment. Why it matters: a fine-tuning script and a checkpoint sitting in the same repository an agent is allowed to maintain is a privilege-escalation path into the model itself, and neither alignment training nor training-data hygiene survives it. [SecurityWeek](https://www.securityweek.com/ai-agents-can-retrain-own-models-mid-task-leaking-secrets-and-erasing-refusals/)

And the Amatera and Remus infostealers now collect access tokens, MCP configurations, prompt histories, and project data stored by AI tools. Why it matters: the third one is the immediate one. An MCP configuration file is a list of what an agent can reach plus the credentials to reach it, and it is now an explicit collection target. ### ✨ New this cycle

**`🔵 TRIAL` Anthropic R&D Automation Index (task tree scored on an AL0 to AL5 automation scale, weighted by person-time).** The method is fully specified and vendor-independent: sample staff to enumerate granular tasks, organise them into a hierarchical tree, score each leaf on a published automation scale, weight by person-time to aggregate. Anthropic ran it over roughly 15,000 tasks in 542 nodes and 378 leaf categories. This is the first published method for answering "how much of our engineering work do agents actually do" that produces a number you can compare across quarters, rather than a developer survey. TRIAL rather than ASSESS because a scaled-down version is runnable against one team's task tree without any vendor dependency, and the output is directly useful to the agent-spend attribution question the Ramp Labs entry raises. The caveats are Anthropic's own and they matter: it is a snapshot, and the safety-versus-capability classification is ambiguous. [[2026-09-18]]

**`🟡 ASSESS` One-token-ahead prerouter expert prefetch (Edge0).** A per-layer neural head predicts the next layer's routing decisions one token ahead so SSD reads for the needed experts start before the current layer finishes. This is the specific mechanism that makes expert offload work at all, since the reads otherwise cannot begin early enough to hide behind compute. Measured at 20.4 tok/s in 2.9 GiB against 3.9 tok/s and 18.2 GiB fully resident on a Mac mini M4 Pro, within a few points of the fp16 teacher across five benchmarks. ASSESS rather than TRIAL because it needs the recovery LoRA to hold quality, results are single-paper and single-hardware, and the interesting application is not local inference but whether the same prefetch scheduling transfers to server-side storage tiering. [[2026-09-18]]

**`🟡 ASSESS` Ternary weights with FP16 group-wise scaling (Bonsai 2 27B).** Ternary (−1, 0, +1) weights at 1.76 effective bits, 5.9GB total for a 27B model, 98.2% of aggregate benchmark performance retained, Apache 2.0 weights, with working CUDA and MLX kernels. Retention against full precision improved from 95% to over 98% in two months. Paired with the BITCOS ternary-compression paper from [[2026-09-17]], this is now a direction with both a theoretical result and shipped kernels in the same week. ASSESS because "98.2% of aggregate benchmark performance" averages over exactly the per-task regressions that decide whether it is usable, and nobody has published a per-task breakdown. [[2026-09-18]]

**`🟡 ASSESS` Bend `LAWS.bend` proof-gated agent codegen.** Declare invariants in a laws file; the compiler demands mathematical proof that they hold on every edit, so an agent that violates one cannot compile and must retry. Every verification gate currently on the radar, including the independent-evidence-source gates and the ImpactGate structural-decay gate, checks evidence or structure after generation. This makes the violating state unrepresentable instead, which is strictly stronger and strictly narrower, since it only covers properties you can state as a law. ASSESS not TRIAL: adopting it means adopting a new language, and nothing here is incremental. The idea is worth understanding regardless of whether Bend is the vehicle. [[2026-09-18]]

**`🟡 ASSESS` Huawei Cloud AgentArts and openJiuwen.** Enterprise agent platform on four stated capabilities: production-grade long-running tasks, enterprise-grade security, industry knowledge, and end-to-end observability, with an open-source edition sharing over 90% of the enterprise kernel.
